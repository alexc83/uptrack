# UpTrack — portable coding-agent instructions

**This is the authoritative shared instruction file for Claude Code, OpenAI Codex, Google Antigravity and Mistral Vibe.** Client adapters may direct agents here but must not redefine the rules.

## First actions (every new task/session)
1. Read `AGENTS.md` and `context/migration/master-plan.md`, `context/migration/migration-status.md`, `context/migration/architecture.md`, `context/migration/feature-inventory.md`.
2. Read `context/project-overview.md`, `context/coding-standards.md`, `context/ai-interaction.md`, `context/current-feature.md` when those original repo files are present.
3. Determine active milestone; read its spec and related actual Angular/backend code. State the active spec status and current git branch.
4. If no spec is READY, do **read-only** inspection and prepare that milestone's detailed spec; stop for user approval before writing application code.

## Product / technical reality
Angular 21 + PrimeNG in `frontend/`; new React + strict TS + Vite + Flowbite React + Tailwind CSS 4 in `frontend-react/` after M03. Java 21 / Spring Boot 3.5.x in `backend/`. Active backend config uses **PostgreSQL**, even though some legacy docs refer to MySQL; treat source/config as authoritative for observed setup.

## Scope and safety
- Preserve every existing user-visible workflow; do not expand product scope.
- Keep `frontend/` read-only, do not remove it. Keep `backend/` and API/DB contracts unchanged unless separately approved.
- Do not expose credentials, secret values, real health records, seed passwords or auth tokens in logs or commits.
- Prefer Flowbite React components, Tailwind layout, minimal custom CSS; React Router, TanStack Query, native fetch, React Hook Form/Zod. No extra UI/state library without approval.
- Never silently alter acceptance criteria, skip error/empty/mobile/auth states or claim tests ran without evidence.
- Follow the canonical Git attribution policy: all commits must use the repository owner identity (`alexc83 <alexc83@users.noreply.github.com>`) and must never attribute author, committer, or commit message trailers (`Co-Authored-By`, `Signed-off-by`, `Generated by`) to AI agents.

## Milestone lifecycle
1. Read and refine DRAFT spec after code audit.
2. Present READY spec to human and request approval. Do not start coding without approval.
3. Check git status; create approved milestone branch.
4. Implement only approved scope, write tests.
5. Run **targeted** tests plus typecheck/lint/build and focused browser checks for what you changed, per `context/testing-workflow.md`; record output, failures and NOT RUN/PENDING-OWNER limitations. Full regression suites are the project owner's by default.
6. Fill `context/migration/verification/mxx-report.md`; update tracker and original current-feature record as appropriate.
7. Explain changed files, evidence, deviations and blockers. Request permission before **each** commit, merge and branch deletion. Never push without user authorization.
8. Advance to next milestone only after merge and tracker update.

## Stops / escalation
If tests cannot run, report blocker and do not claim parity. If 2–3 grounded fixes fail, stop rather than random retries. Ask before architecture changes, destructive operations, schema updates, dependency additions outside spec, modifying git history, deployments, and branch deletion.

## Verification
**Testing policy (canonical: `context/testing-workflow.md`).** Agents run targeted tests, typecheck, lint, build and focused browser tests for their changes, investigate failures they introduce, and do not repeatedly run full suites unless the owner authorizes it, a regression needs diagnosing, or risk warrants it (state why). The owner runs the full unit/integration and four-browser Playwright suites, approves screenshot baselines (Edge/macOS only; agents never regenerate them) and performs live-backend acceptance. Report exactly which tests ran and which are pending; never call a milestone fully verified from targeted checks alone.

For React milestones after M03: `npm run typecheck`, `npm run lint`, `npm run test -- --run`, `npm run build` (from `frontend-react/`, after scripts are set up). For backend-impacting changes: `./mvnw test` and appropriate package build from `backend/`. Verify relevant browser scenarios with test accounts and screenshots when accessible. Never claim a command exists until the scaffold defines it.

## Cross-agent handoff
Make all decisions durable in specs, tracker and verification files; do not depend on chat memory or agent-specific plans. At handoff report active step, branch, spec status, exact tests run, known issues, next action.

## Git branch lifecycle (canonical)
- Until M14, `main` is the stable integration branch and may contain legacy Angular and accepted React milestones. Integration is not deployment approval or authorization to switch production traffic; production cutover requires separate M14 approval.
- Create one short-lived milestone branch from current main. Implement/test there; obtain milestone acceptance before integration. No long-lived React migration branch is required.
- **Integration (since D01-E, 2026-11-04):** changes reach `main` only through a pull request; **direct pushes to `main` are prohibited**. Ruleset `Require CI and pull requests on main` (26574227) requires a pull request (0 approvals) and the four passing GitHub Actions checks `backend`, `backend-postgres`, `frontend` and `e2e-chromium`; branches need not be up to date with `main`. **Merge commits are the approved integration method** (`gh pr merge --merge` or the GitHub merge button); do not fast-forward push, squash-merge or rebase-merge into `main`. `Protect main` (26409215) keeps blocking deletion and non-fast-forward updates.
- **No routine bypasses:** never use `--admin`, never edit, disable or work around a ruleset to get a merge through, and never merge with failing or pending required checks. The owner-only break-glass procedure is in `context/testing-workflow.md` ("Branch protection and break-glass recovery"). Firefox/WebKit (`browsers.yml`) are informational nightly/manual checks, not required; CodeQL and Vercel are not required either.
- Never automatically squash, rebase, reset, force-push or rewrite historical commits. If a pull request cannot be merged by a merge commit, stop for an owner decision.
- Commit, push, merge (including opening/merging pull requests), branch deletion and any change to repository settings or rulesets require owner authorization; an explicit authorization may cover the named sequence. After an authorized pull-request merge, fetch and verify local main and origin/main agree, ahead/behind is 0/0, and feature commits are ancestors of main (via the merge commit).
- Then safely delete the merged local milestone branch with `git branch -d`. Delete its remote counterpart only if it exists, is confirmed merged and owner authorization covers deletion. Prune obsolete tracking references as appropriate. Preserve unmerged, uncertain, active and Dependabot branches. Record actual integration and cleanup in the final handoff.
